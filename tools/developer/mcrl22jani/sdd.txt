As a first approximation, this version doesn't consider data at all, so no process functions / families or instances. Also no actions with data, only actions and their synchronization. And no choice quantification. There's also no conditional operator since there is no data to make predicates about.

We'll later deal with actions with data and their synchronization when one sends (e.g "a(n)") and one receives (e.g "sum b:Nat b(n)")

The first objective is to get the locations and edges as close to what the final product should be.

We'll now focus on synchronization and communication. I.e we'll be translating `||`, `comm`, `allow`, `block`, `rename`, `hide`.

Most of the rules should be effects on a global `syncs` structure we'll keep track off. Initially this structure should include the vectors needed to allow any automaton to perform any action in the action declarations section. As we traverse the AST, we'll associate statements to operations to perform on this structure. Once we're done, we should have a correct sync matrix that allows, renames, communicates and hides all the actions according to operations.

We should also somehow keep track of the with of the matrix.

Problem solved: the right-hand side of the sync matrix is the one keeping track of both allowed and visible transitions, which are the things over which comm, allow, block, rename and hide operate. Then the translation can be carried out as follows:

Traverse the parallel composition tree depth first, finding leafs (process instances). When encountering a leaf, annotate it with a $n x 2$ matrix to allow it to perform any action independently.

When processing non-leaf nodes, check the operator used and apply a version of the operator that works on the matrices annotated in it's process operand. Annotate the node with the resulting matrix.

And so on and so forth.
